# API contract (MVP, v1)

Base path `/v1`. JSON in English. Errors: `{"error": {"code": "STABLE_CODE", "message": "..."}}`; the app translates `code`.
Auth: short-lived access JWT + refresh token. The OpenAPI generated by FastAPI is the real contract; keep this file in sync.

## Meals

| Method | Path | Notes |
| --- | --- | --- |
| POST | /meals | multipart photo. Resize → `FoodVisionProvider` → discard photo → save → update pet and points. Returns `{meal, pet, events[], pet_tip}` (`pet_tip` Premium only) |
| POST | /meals/manual | RF-95. `{items: [str], meal_type}` chosen by hand when the photo cannot be read. Same `{meal, pet, events[]}` as `POST /meals` |
| GET | /meals | `range=today|7d|30d`, cursor pagination |
| GET | /meals/{id} | |
| PATCH | /meals/{id} | correct items and meal type; points do not change |
| DELETE | /meals/{id} | soft delete with 5 s undo on the client; points do not change |
| DELETE | /meals | erase every meal record (hard delete). Always free; works without `meal_data` consent. Answers 200 `{deleted: n}`. Account, pet, points, lives and streak stay |

Manual entry (`POST /meals/manual`) counts as a log for the pet (same lives, streak and points rules, including the
3 scored meals per day shared with photo logs), never calls the vision provider and never consumes the AI photo limit.
Errors: 403 `MEAL_CONSENT_REQUIRED`, 422 `VALIDATION_ERROR` (1 to 30 items of 1 to 80 chars after trimming, `meal_type`
one of `breakfast|lunch|dinner|snack`).

Errors for `POST /meals`: 403 `MEAL_CONSENT_REQUIRED`, 429 `DAILY_LIMIT_REACHED`, 422 `PHOTO_NOT_READABLE` / `NOT_FOOD`
(do not consume the limit), 503 `VISION_UNAVAILABLE` (does not consume the limit).

## Vision result (Pydantic model)

```
description: str            # in the user's language
items: list[str]
meal_type: breakfast | lunch | dinner | snack
food_groups: list[str]      # fixed vocabulary, e.g. grains, legumes, protein, vegetables, fruits, dairy
item_count: int
colors: list[str]
confidence: float           # 0..1
plate_share: dict[str, float]   # fraction per food group (Premium view)
new_foods: list[str]        # items not seen in the user's last 30 days (Premium view)
```

Never: calories, macros, grams, scores, health labels. The pet tip comes from an approved phrase list in code.

### Vision pipeline (`be/app/vision`)

Every adapter runs behind `VisionPipeline`, so plugging in a provider never changes these rules:

1. Size (`MAX_UPLOAD_BYTES`) and real image type are checked before any provider call (RNF-22): JPEG, PNG or WebP
   decoded by Pillow. HEIC/HEIF is accepted by the route but Pillow cannot decode it yet, so it answers
   `PHOTO_NOT_READABLE` (the app should send JPEG).
2. Resize to at most 1024 px on the long side, EXIF orientation applied, re-encoded as a fresh JPEG with no EXIF,
   GPS, ICC or XMP. The provider receives only these bytes plus the language tag: never a name, e-mail or id.
3. One call per attempt with `VISION_TIMEOUT_SECONDS` (default 5); one retry on timeout only.
4. The answer is re-validated with `VisionResult`; `food_groups` and `plate_share` keep only the fixed vocabulary
   `grains, legumes, protein, vegetables, fruits, dairy`; any description or item that mentions calories, macros,
   grams, scores or health labels is dropped; `item_count` is the number of items.
5. Errors: unreadable photo `PHOTO_NOT_READABLE`, too large `PHOTO_TOO_LARGE`, not food `NOT_FOOD`, provider error,
   bad answer or two timeouts `VISION_UNAVAILABLE`. None of them consumes the daily limit or writes anything.

The prompt is one versioned template (`be/app/vision/prompt.py`, `PROMPT_VERSION`). Each photo meal stores
`vision_provider`, `model_version` and `prompt_version` (internal; not returned by the API).

### Pet tip (Premium, "Seus hábitos")

`POST /meals` answers `{meal, pet, events[], pet_tip}`. `pet_tip` is a pt-BR string for Premium users and `null` on
Free, for manual meals and when no food group is missing. It is picked from the approved list in
`be/app/domain/tips.py`, only from the food groups missing on the plate (rotated by local day), never AI text. Tips
only ever suggest adding something ("Que tal uma fruta no lanche?").

## Notifications

| Method | Path | Notes |
| --- | --- | --- |
| POST | /push-tokens | `{token, platform: "ios" or "android"}`. Registers or refreshes an Expo push token (`ExponentPushToken[...]` / `ExpoPushToken[...]`). Answers 201 `{token, platform}`. A token seen again moves to the user that sent it last (same phone, another account). Needs no meal consent. |
| DELETE | /push-tokens/{token} | 204. Removes the caller's own token; idempotent (a missing or foreign token is not an error). |

`GET /me` and `PATCH /me` carry the preferences in `notifications`:

```
"notifications": {
  "meal_reminder": true,        // notice when the pet is tired
  "sleepy_notice": true,        // notice when the pet is sleepy
  "weekly_summary": true,       // stored only; the weekly summary is not sent yet
  "quiet_hours_start": "22:00", // local time of the user, HH:MM (may cross midnight)
  "quiet_hours_end": "08:00"
}
```

`PATCH /me` accepts any subset of these fields inside `notifications`; fields not sent keep their value. Bad
`HH:MM` or unknown keys answer 422 `VALIDATION_ERROR`. `start == end` means no quiet hours.

### Notice rules (ARQ worker, RF-40 to RF-42)

The worker (`uv run arq app.worker.settings.WorkerSettings`) runs `send_notices` every 15 minutes. It reads the mood
computed by the domain (it settles the pet in memory and **never writes lives**) and sends at most:

- one `tired` notice and one `sleepy` notice per episode (an episode is the stretch since the last log, so a new log
  starts a new one); a pet that never logged is a single episode;
- none when the mood is `happy`, `paused` or `fainted`;
- none inside the user's quiet hours (local time, DST aware, end exclusive) or when the matching switch is off;
- at most 2 notices per local day;
- only to users with the `meal_data` consent, no pending deletion and at least one push token.

Each decision is stored in `notice_log` (unique per user, kind and episode) before it is pushed, so nothing is sent
twice even if a worker crashes or runs twice. Copy comes from a fixed pt-BR list in `app/domain/notifications.py`
(no free text, no body, weight, calories or right/wrong food). Tokens that Expo reports as `DeviceNotRegistered`
are deleted. The Expo adapter is `providers/expo_push.py` (`PUSH_PROVIDER=expo`, optional `EXPO_ACCESS_TOKEN`);
`PUSH_PROVIDER=fake` records messages and is refused in production.

### Account hard delete (ARQ worker)

`purge_accounts` runs daily at 03:17 UTC. For accounts with `DELETE /me` pending for more than
`DELETION_GRACE_DAYS` (30): meals, points, pauses, pet, push tokens, notice log and usage are deleted and the user
row is anonymized (`anonymized_at` set, email `deleted-<id>@deleted.invalid`, no name, no password). Consent
records and the subscription row stay for 5 years (retention table in `product-rules.md`), then the row is removed.
An anonymized account cannot sign in or refresh a token. The job is idempotent.

## Implementation notes (backend, Stage 1)

Implemented: `/auth/register|login|refresh`, `/auth/password/forgot|reset`, `/consents`, `/me` (GET, PATCH, DELETE, `/export`), `/pet` (GET, PATCH),
`/pet/pause` (POST, DELETE), `/meals` (POST, POST `/manual`, GET, GET `{id}`, PATCH, DELETE), `/push-tokens` (POST, DELETE),
notification preferences in `/me`, the notice and hard delete ARQ jobs (see Notifications), `/health`, `/health/ready`.
Not yet: Google/Apple login, billing endpoints, webhooks.

- `/health` and `/health/ready` live at the root (no `/v1`). Ready answers 503 with `{"status": "unavailable", "checks": {...}}`.
- Register body: `email`, `password` (8+ chars), `name`, `adult_confirmed` (must be `true`, else 422 `ADULT_CONFIRMATION_REQUIRED`), optional `timezone` (IANA, default `America/Sao_Paulo`).
  Auth answers `{access_token, refresh_token, token_type, expires_in}`. Refresh tokens are stateless JWTs (no rotation yet).
- Password reset: `forgot` e-mails a link `<PASSWORD_RESET_URL>?token=...` (default `papeto://reset-password`;
  the final deep link or web page is not decided) through `EmailProvider` (the fake adapter only records it).
  The token is random (256 bits), single use, valid `PASSWORD_RESET_MINUTES` (default 60); only its SHA-256 hash
  is stored. A successful reset marks every open token of the user as used. At most `PASSWORD_RESET_MAX_PER_HOUR`
  (default 3) e-mails per account per hour; extra requests still answer 202 and send nothing. There is no per-IP
  rate limit yet, and existing refresh tokens stay valid after a reset (they are stateless).
- `DELETE /me` answers 202 with `deletion_scheduled_for` (now + 30 days). Signing in again cancels it. After the grace period the `purge_accounts` job erases the data (see Account hard delete).
- `GET /meals`: `range=today|7d|30d` (local days of the user), `limit` (1..50, default 20), opaque `cursor`; answers `{items, next_cursor}`.
- Every meal object has `source`: `photo` (vision provider) or `manual` (RF-95). A manual meal has `description: ""`,
  empty `food_groups`, `colors` and `plate_share`, and `confidence: 1.0`.
- All meal endpoints need an active `meal_data` consent (403 `MEAL_CONSENT_REQUIRED`). Export and account deletion never do.
- `POST /meals` accepts JPEG, PNG, WebP or HEIC up to `MAX_UPLOAD_BYTES` (default 8 MiB): wrong type 422 `PHOTO_NOT_READABLE`, too large 413 `PHOTO_TOO_LARGE`. HEIC passes the route but is not decodable yet (see Vision pipeline).
- A new pet has `name: null`: the app shows screen 43 (Name your pet) while `GET /pet` returns `null`, then sends
  `PATCH /pet {"name": "..."}` (1 to 20 chars after trimming, else 422 `VALIDATION_ERROR`). A name cannot be cleared back to `null`.
- Pet `color` is a lowercase token (`^[a-z0-9_-]{1,20}$`, default `default`) until the palette is decided.
- `GET /pet` events: `life_lost` is returned once, relative to the lives the server last returned to this user.

### Consent revocation

- `POST /consents` with `accepted: false` for `meal_data` takes effect immediately: every meal endpoint
  (`POST /meals`, `POST /meals/manual`, `GET /meals`, `GET|PATCH|DELETE /meals/{id}`) answers 403
  `MEAL_CONSENT_REQUIRED`. `GET /me/export`, `DELETE /me`, `DELETE /meals` and `GET /pet` keep working.
- The response carries `suggested_actions`: for a `meal_data` revocation it is
  `["export", "delete_meals", "delete_account"]` (the app offers `GET /me/export`, `DELETE /meals` and `DELETE /me`);
  otherwise it is `[]`. Accepting again returns `[]`.
- `analytics` consent: `accepted: false` sets `analytics_opt_out = true`, `accepted: true` sets it to `false`
  (same flag as `PATCH /me`).

### Support hint (RF-98)

`GET /pet` returns `support_hint: bool`. It is `true` only when the risk-pattern rule is enabled and the user had
no log on `PetRulesConfig.risk_pattern_days` completed local days in a row (paused days and days before the pet existed
do not count; a log today clears it). The rule is **disabled by default** (`risk_pattern_days = None`, threshold
not decided), so the field is always `false` today. The app shows a kind message and the CVV 188 path; it never
changes lives, points or streak. See `docs/domain/pet-rules.md`.

### Product events (RF-70)

Emitted through `AnalyticsProvider` after the transaction commits. The `distinct_id` is an HMAC-SHA256 of the user id
with `ANALYTICS_ID_SECRET` (falls back to a value derived from `JWT_SECRET`), 32 hex chars: stable per user,
not reversible without the secret, never a name or email. Properties are enums or counts only (no free text,
meal text, photo, name or email). Nothing is emitted when the user has `analytics_opt_out = true`. Analytics errors
never fail a request.

| Event | When | Properties |
| --- | --- | --- |
| `signup_completed` | `POST /auth/register` | none |
| `consents_accepted` | `POST /consents` with `accepted: true` | `type` |
| `pet_named` | first `PATCH /pet` that sets a name | none |
| `meal_logged` | `POST /meals`, `POST /meals/manual` | `source`: `photo` or `manual` |
| `life_lost` | the server first sees lives below the last seen value (`GET /pet`, `PATCH /pet`, meal log) | `lives_left` |
| `pet_fainted` | same moment, when lives reach 0 | none |
| `pet_woke_up` | a log while fainted | none |
| `notification_sent` | a notice reached at least one device | `kind` |
| `account_deletion_requested` | `DELETE /me` (first request) | none |
| `export_requested` | `GET /me/export` | none |

Return-after-faint metric (no dashboard): for each `pet_fainted` event of an id, count it as returned when the same
id has a `meal_logged` within 7 days after it. `pet_woke_up` is the first `meal_logged` after a faint. Limit: faint
is detected when the server first sees it (app open or log), not at the exact midnight; users who never open the app
again after fainting emit no `pet_fainted` (the notice job does not save pet state). Adapter: `ANALYTICS_PROVIDER`
= `noop` (default, disabled) | `fake` (not in production) | `posthog` (needs `POSTHOG_API_KEY`, optional
`POSTHOG_HOST`); plain httpx, no SDK, no person profiles.

Stable error codes: `UNAUTHORIZED` 401, `INVALID_TOKEN` 401, `INVALID_CREDENTIALS` 401, `EMAIL_ALREADY_REGISTERED` 409,
`ADULT_CONFIRMATION_REQUIRED` 422, `INVALID_TIMEZONE` 422, `VALIDATION_ERROR` 422, `MEAL_CONSENT_REQUIRED` 403,
`DAILY_LIMIT_REACHED` 429, `PHOTO_NOT_READABLE` 422, `PHOTO_TOO_LARGE` 413, `NOT_FOOD` 422, `VISION_UNAVAILABLE` 503,
`PREMIUM_REQUIRED` 402, `MEAL_NOT_FOUND` 404, `PET_NOT_FOUND` 404, `PET_ALREADY_PAUSED` 409, `PET_NOT_PAUSED` 409,
`INVALID_CURSOR` 422, `INVALID_RESET_TOKEN` 400, `NOT_FOUND` 404, `METHOD_NOT_ALLOWED` 405, `INTERNAL_ERROR` 500.
